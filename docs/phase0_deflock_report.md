## §1 コード読み取り

### §1-1 Step3プロンプトの現文言

`build_mora_rewrite_prompt`（`app/services/stepwise_waka_generator.rb:476-490`）の全文：

```ruby
def build_mora_rewrite_prompt(free_text, feedback)
  feedback_note = feedback ? "※前回の書き換え「#{feedback[:ku]}」は#{feedback[:issue]}でした。#{feedback[:message]}\n" : ""

  <<~PROMPT
    以下の和歌の意味や情景のニュアンスを保ったまま、五・七・五・七・七（合計三十一音）の形に書き換えてください。
    三十一音を超えないこと。短すぎるのも誤りです。区切り記号（／や・など）は使わず、一続きの文として書くこと。
    #{feedback_note}
    【書き換え対象】
    #{free_text}

    【出力形式】
    書き換えた和歌だけを一行で出力してください。見出し・説明・前置き・引用符は不要です。
    書き換え：
  PROMPT
end
```

**指示語の強度・条件（固定部分）**：
- 「三十一音を超えないこと」＝**上限方向のみ明示**（超過の禁止）。「短すぎるのも誤りです」は
  下限があることを述べるのみで、具体的な下限値・操作は指示していない。→ 圧縮バイアスの土壌になり得る
  （案6が問題視する点と一致）。
- 「一続きの文として書くこと」＝区切り記号を禁じているため、Step4が期待する「17音めの語境界」を
  モデルは意識する手立てがない（`investigation_step3_mora_phase0.md` 欠陥Aの指摘と同じ）。

**方向性フィードバック（feedback_note、`extract_and_validate` = `stepwise_waka_generator.rb:226-267` が生成）**：

| 分岐 | issue | message |
|---|---|---|
| 前句エコー | `"前句エコー"` | 「前句をそのまま繰り返さず、新しい言葉で三十一音に書き換えてください」 |
| 句切れ不自然 | `"句切れ不自然"` | 「句のはじめが助詞や読点、または句の終わりが「の・に・を・て」などで終わっています。…」 |
| 音数逸脱 | `"#{total_mora}音（三十一音から#{TOLERANCE}音超逸脱）"` | 「現在#{total_mora}音です。#{増減の指示}、合計三十一音（三十〜三十二音）に収めてください。助詞を削って字を詰め込みすぎないこと。」（`need`の符号で「あとN音、言葉を補って増やして」／「N音、説明的な部分を削って減らして」を出し分け＝**其の八十四案5で既に方向・量を明示化済み**） |
| 区切り不一致 | `"区切り不一致"` | 「はじめの十七音で言葉がひとつ切れ、そのあと十四音が続くように…」 |

feedbackは方向・量とも既に操作的（案5実装済み）。ただし「助詞を削って字を詰め込みすぎないこと」の一文が
**too_short方向でも一律に付く**ため、不足時にも「削れ」の語が視界に入る余地がある（軽微だが要注意）。

**deflock判定の条件と発動タイミング**：`rewrite_and_extract`（`:166-200`）内。
```ruby
temp = [temp + 0.3, 1.1].min if mora_text.present? && mora_text == prev_text
prev_text = mora_text
```
直前attemptの出力**文字列が完全一致**した場合のみ温度を+0.3（上限1.1）する。
「実質同じだが表記が1文字違う」場合は非該当（deflock検出は完全一致ベースで緩い救済しかない）。

### §1-3 Step1.5のスキップ条件

依頼書は「free_textが既に29-33音ならStep3をスキップ（案2）」「tolerance:引数（案1）」の2点を
1つの「Step1.5のスキップ条件」として問うているが、**実装上は3つの別機構**であり、うち1つは
Step1.5（`adjust_free_verse_length`）とは無関係である点をまず訂正する。

1. **Step3前ゲート（其の八十四 案2）** — `rewrite_and_extract`冒頭（`:169-175`）:
   ```ruby
   pre_seg, = extract_and_validate(free_text)
   if pre_seg
     ...
     return pre_seg[:surface]
   end
   ```
   これは**Step1.5の関数ではなくrewrite_and_extract内の独立処理**。free_textが
   `extract_and_validate`（後述§1-4）を素通しで通過できるなら、Step3を一切呼ばずに採用する。
   条件は「29-33音」という単純な範囲チェックではなく、**Step4と全く同じ判定関数**
   （総モーラ29-33 かつ 境界tolerance:1で17/14音の形態素境界が見つかる かつ 前句エコーでない
   かつ `clean_phrase_edges?` を満たす）である。したがって「29-33音であること」は必要条件だが
   十分条件ではない。

2. **境界tolerance:1（其の八十四 案1）** — `extract_mora_segment(ms, skip, take, tolerance: 1)`
   （`extract_and_validate`内、`:231`）。総モーラ数とは別に、17音／14音の**形態素境界の位置**を
   ±1音の近傍まで許容する。`boundary_index_near`（`verse_text_analysis.rb:62-76`）が
   target±toleranceの範囲で最も差の小さい境界を選ぶ。

3. **真のStep1.5（`adjust_free_verse_length`、`:136-159`）** — 上記1・2とは独立した、
   Step1出力の**極端な**長さ（`FREE_VERSE_MORA_LONG_THRESHOLD = 50`超／
   `FREE_VERSE_MORA_SHORT_THRESHOLD = 25`未満）のみを補正する推敲。
   **25〜50音の範囲は無条件で無補正のままStep3へ渡る**（境界値は含む: `>50`/`<25`が発動条件なので
   ちょうど25・50は補正対象外）。

**境界値のまとめ**：

| 機構 | 対象範囲 | 判定内容 |
|---|---|---|
| Step1.5（音数調整） | `<25` → expand、`>50` → condense | 総モーラ数のみ、粗い補正 |
| Step3前ゲート（案2） | 実質29-33（＋境界±1＋端の自然さ＋エコー無し） | Step4と同一の厳密判定 |
| Step4抽出（tolerance:1） | 29-33（＋境界±1） | 案2と共有関数、数値上の差はゼロ |

### §1-4 Step4の抽出境界とStep1.5との連続性評価

`waka_extraction_bounds`（`:324-326`）：chouku=`[skip:0, take:17]`、tanku=`[skip:17, take:14]`。
`extract_and_validate`（`:226-267`）が`WAKA_TOTAL_MORA=31 ± WAKA_TOTAL_MORA_TOLERANCE=2`（29-33）と
`tolerance:1`の境界許容を課す。

**§1-3の案2（Step3前ゲート）とStep4はコード上完全に同一の`extract_and_validate`を呼んでおり、
両者の間に数値的な断絶（デッドゾーン）は存在しない**。依頼書が想定した「29-33（skip条件）と
30-32（Step4境界）の間のデッドゾーン」という仮説は、実装を確認した限りでは**該当箇所が無い**
（Step4の境界は「30-32」ではなく「29-33＋境界tolerance1」であり、案2の条件と数値的に同一）。

**実際に存在するデッドゾーンは、Step1.5（真の音数調整）としきい値29-33の間**にある：

- Step1.5が補正するのは `<25` と `>50` のみ。
- Step3前ゲート／Step4が受理するのは実質29-33（＋境界条件）。
- **25-28音、34-49音の範囲は、どちらの機構にも捕捉されずStep3に生のまま渡る**。

§2の実測で示す通り、run100のfree_text（168件）のうち **166件（98.8%）がこの25-49音の
無補正ゾーンに該当**しており、これは8/30の`investigation_step3_mora_phase0.md`が指摘した
欠陥C（デッドゾーン仮説）と同一の問題が、其の八十四〜八十五で実装された案1/2/5後も
**未修正のまま残っている**ことを意味する（案1/2/5はStep4抽出の緩和とdeflock検出であり、
Step1.5の閾値自体には手を付けていないため、当然の結果）。

## §3 案の実現性評価

### 案6：Step3プロンプトの圧縮バイアス是正

- **評価**：§1-1・§2-3の実測により、「圧縮」指示が一方的に支配的とは言えない
  （too_long 31.4% vs too_short 35.0%、ほぼ拮抗）。したがって**「高域偏重（34-41音）の原因文言」を
  単一の圧縮バイアス文言に特定することはできない**。むしろ2-2で見た二山（25-28と34-37）は
  「短すぎ」「長すぎ」の両方向に同程度発生しており、プロンプトが**両方向とも数値的な目標を
  与えていない**（「三十一音を超えない」「短すぎるのも誤り」という定性的表現のみ）ことが
  共通原因と考えられる。
- **単独での実装可否**：文言のみの変更で低コストだが、**単独では二山のどちらも解消しない**
  （8/30調査の結論「案6のみは非推奨」が今回のrun100データでも裏付けられた）。

### 案3：Step1.5↔Step4閾値整合（デッドゾーン解消）

- **評価**：§1-4で確認した通り、**デッドゾーンは実装上明確に存在する**
  （Step1.5の補正域`<25`/`>50`と、Step3前ゲート/Step4の受理域`29-33`の間、
  すなわち`25-49`が無補正）。依頼書が想定した「案2条件とStep4境界の間」ではなく
  「Step1.5としきい値29-33の間」が正しい所在。
- **実データでの裏付け**：run100のfree_text 168件中166件（98.8%）がこのデッドゾーンに該当。
  8/30調査時点の推定（38/129 draft ≒ 29%）よりも**遥かに広い範囲（ほぼ全数）が該当**しており、
  問題の規模はむしろ拡大している（Step1のペルソナ・視座指示が音数を意識しない自由詠みを
  強く促す設計のため、25-49音に広く分布するのは構造的に必然）。
- **実現性**：8/30調査の案3案（閾値を`[25,50]`→`[29,34]`に狭め、`:expand`/`:condense`
  プロンプトに具体的な過不足音数を数値で渡す）はそのまま適用可能。コスト・リスクは
  「小〜中」（定数変更＋プロンプト文言＋`total_mora_of`の結果を渡す配線）で、
  既存の`build_length_adjust_prompt`（`:493-515`）を数値注入版に拡張するだけで済む。
  **今回のPhase0時点でも変更不要と判断できる材料は無く、むしろ最優先で着手すべき根拠が
  実データで補強された。**

### 案4：知識蓄積型2段プロンプト

- **既存Step0との差分**：`:waka_extraction`経路には「前句見立て言語化」に相当するStep0は
  **存在しない**。`:direct`方式の`RengaGenerator`にある「Step0」（`renga_generator.rb:50`
  付近、其の七十九 案A）は**季節転換の感覚ドメインをRuby側でローテーション決め打ちする**もので、
  目的も実装も別物（LLMに何かを言語化させる機構ではない）。したがって案4は
  **既存資産の転用ではなく新規実装**になる。
- **追加Ollamaコスト概算**：現行run100の`step3`呼出は639回、`elapsed_sec`実測はおよそ3.4〜3.8秒/回
  （ログのelapsed_secサンプルより）。総計約2,200〜2,400秒（37〜40分相当）。
  2段プロンプト化の場合：
  - 1コール内でCoT的に「句割り宣言→本文」を書かせる場合：入出力トークン量が2〜3倍に増え、
    1回あたりの所要時間もほぼ比例して増加すると見込まれる（1回5〜8秒程度に増加想定）。
  - 2コールに分割する場合：呼出回数が2倍になり、モデルロード状態は維持されるため
    レイテンシは概ね加算（1回あたり計6〜7秒程度）。
  - どちらの方式でも、8/30調査の見立て（リトライ回数が4.8回→2回程度に減れば総コール数は
    純減し得る）が成立すれば総時間は現状と同等かやや改善、成立しなければ2倍以上に悪化する
    ため、**不確実性が最も大きい**。
- **評価**：効果ポテンシャルは高いが、実装・検証コストが3案中最大。今回のPhase0データは
  案3で説明できる範囲（デッドゾーン起因の失敗）が非常に広い（98.8%）ことを示しており、
  **案3を先に実施して効果を測定してから案4の要否を判断すべき**という8/30調査の結論を
  変える材料はない。

### 推奨実装順序

1. **案3（Step1.5↔Step4閾値整合）を第一候補として実装**。デッドゾーンの実在と規模（98.8%）が
   run100の実データで裏付けられており、低コスト・低リスクで最大の伸びしろが見込める。
2. 案3実装後、10句smokeで二山の残存状況を再測定。**「句切れ不自然」27.4%は案3では解消しない
   別軸の課題**であるため、smoke結果次第で案6（プロンプト文言）や、`clean_phrase_edges?`周りの
   追加ガードを検討する。
3. 案3（＋必要なら案6）で二山が解消しない場合にのみ、コスト最大の**案4（2段プロンプト）を
   本命として着手**する。8/30調査時点の結論を踏襲し、温存する。

**変更は行っていない**（本Phase 0のスコープ通り）。
