### R2-2 句去の間隔の決め方（部立 vs 語単位の優先）

【事実】**優先関係はない。両方が独立に走り、結果が連結される。** `all_violations`（`shikimoku_checker.rb:202-217`）は `kuzari_violations + kukazo_violations + nanaku_gomono_violations` を単純連結する。同じ語が部立ルールと七句去物の両方に当たれば、違反が2件出る（月：光物3 と 七句去物7 の両方）。重複排除・上書きの処理はない。

- 部立ルールは `kuzari_rules.yml`（部立→整数、植物のみ `{default:5, cross:3}`）。
- 語単位ルールは七句去物（全語7固定）と一座一句物（二度目不可）。
- **間隔の数え方**：`between >= interval - 1 + interval_offset` なら合法（`:122`）。つまり「3句去」は**差3（間に2句）で合法**。七句去物は `interval >= 7`（`:408`、差7＝間に6句）。`interval_offset: 1`（瀬田2016）なら「間にinterval句以上」。【推測】山内の「可隔三句物」「可隔五句物」の「隔」を何句と数えるかとの対応は未確認（人間判断：後述）。
- **`ichiza_violations` は `all_violations` に含まれない**。呼び出し側が別に足している（`app/controllers/rengas_controller.rb:219,239`、`app/services/renga_generation_service.rb:72`）。呼び忘れると一座一句が効かない。【事実】
- `compute_forbidden_nanaku_words`（`:507-518`）は `text.include?(nw)` のみで、`word_in_text?` の yomi 照合を使わない。**生成側の禁止語リストと検査側で表記揺れの扱いが違う**。【事実】

### R2-4 一座規制（ichiza_limit）

【事実】`ichiza_limit` はリポジトリ全体に**出現ゼロ**。一座一句物は「二度目は違反」の二値のみ（`:354-370`）。花は `teiza_hana_violations`（定座）で別管理（`ichiza_ichiku_words.yml` 冒頭コメント）。

実装の入口の候補（【推測】設計案。未実装・未検証）：
1. `ichiza_ichiku_words.yml` の値に `limit: N` を追加し、`ichiza_violations`（`:354-370`）の `hist_seen[iw] ||= i+1` を回数カウントに変え、`count >= limit` で違反。後方互換は `limit` 省略時=1。
2. 「只一・山桜遅桜一・紅葉一」のような枠の割り振りには、語→枠の写像（別キー）が必要。照合は現行の `word_in_text?` では「桜」が「山桜」に部分一致するため、**長い語を先に消費する処理**が要る。
3. 呼び出し側（controller・service）が `ichiza_violations` を別呼びしている点は、`all_violations` へ取り込むかを設計時に決める必要がある。

### R4-3 吹物（風類）の定義

【事実】`吹物`・`風類` の文字列は `app/`・`spec/`・`script/` のいずれにも無い。部立として近いのは `風体`（`kuzari_rules.yml:5`、`kukazo_rules.yml`、`bui_dictionary.yml` の 風・東風・嵐・野分）。

「吹物」を新設する場合、追加・変更が必要な箇所（【事実】は現存の鍵・参照、必要性は推測）：

1. `app/data/kuzari_rules.yml`（および `kuzari_rules_seta2016.yml`）に鍵を追加。ただし `風体` と併存させるか改名するかを決める必要がある。
2. `app/data/kukazo_rules.yml`（および seta2016）の `bui` 鍵。
3. `app/data/bui_dictionary.yml` の 風・東風・嵐・野分 の `primary_bui`（および春風・夜風等を追加するか）。
4. `spec/services/bui_dictionary_futai_spec.rb`、`script/verify_shikimoku.rb:1068`。
5. `renga_generator.rb` の `BUI_EXAMPLE_WORDS`（プロンプト用。現在、風体の例示はそもそも無い）。
6. 【事実】`ShikimokuChecker` 本体の変更は不要。部立名は YAML の鍵として読むだけ（`:94`、`:156`）で、コード内に部立名の直書きは無い。

## 人間の判断が要る点

1. **R4 の修正案の前提確認**：東風が既に風体であること、袖・あはれ・思ふが辞書に無いことを踏まえて、修正案5語の扱い（新規登録するのか、既存の別の版を指しているのか）。
2. **吹物か風体か**：吹物を新設して風体を廃するのか、風体を維持して付録Aの「吹物」は同義とみなすのか。句去は風体5か、光物降物聳物と同じ3か。
3. **「可隔三句物」の数え方**：現行は「3句去＝差3（間に2句）で合法」。山内の「隔」が間に3句なら現行は1句ゆるい（`interval_offset: 1` の瀬田2016方式に相当）。どちらを採るか。
4. **二重発火の扱い**：月・煙・松で部立ルール(3または5)と七句去物(7)が両方発火する。両方残すか、語単位を優先するか。
5. **一座N句物の枠割り振り**（H-2）：桜＝只一・山桜遅桜一・紅葉一 の部分文字列の扱い（長語優先）を、辞書側と実装側のどちらに持たせるか。
6. **ゲート1 fail の扱い**：期待値を `風体` に直す（別依頼書）のか、東風の分類を戻すのか。
7. **涙→恋の影響**：本番百韻で恋の連続上限・句去が新たに発火する可能性（未計測）。実測の依頼を出すか。
