## 0. 結論（要約）

- **「て」止め誤検出という当初仮説は、量的にはほぼ支持されない**。p3 run100の
  句切れ不自然175件中、「て」で終わる誤棄却は**2件（1.1%）のみ**、しかも両方とも
  短句（tanku）だった。水無瀬三吟でも短句が「て」で終わる例は0/50であり、
  **この2件の棄却自体は妥当**と判断できる。
- 一方、**別の誤検出パターンが実データで確認できた**：長句（chouku）が格助詞「に」で
  終わるケースが**14件**棄却されているが、水無瀬三吟では長句の12.0%（6/50）が
  「に」止めで終わっており、これは**古典連歌の正当な技法（余情止め）**である。
  さらに「て／にて」止めも長句の26.0%（13/50）を占め、**長句の38%が「て」か「に」で
  終わる**という強い慣習がある。
- 現在の`clean_phrase_edges?`は`verse_type`（長句/短句）を区別せずに一律の助詞リストで
  判定しており、**長句の「に」止めを誤って棄却する構造的欠陥**が存在する。
  「て」はこのバッチではたまたま長句側で発生しなかっただけで、発生すれば同様に
  誤棄却されるはずである（実装上verse_type非依存のため）。
- 句切れ不自然の最大要因（tail破れの49.6%）は「の」（連体化）止めだが、こちらは
  水無瀬三吟に実質的な用例が無く（唯一の一致は「明けぼの」という単語の末尾がたまたま
  「の」だった誤マッチ）、**現状の棄却は妥当**と判断する。
- Step1.5の発動（condense/expand）と句切れ不自然の相関は、単純集計では強く見えるが
  （45/46フロー）、**Step3流入フロー全体の91.9%がそもそもStep1.5を経由**しており、
  母数を揃えると発動フロー中39.8%・非発動（skipのみ）フロー中10.0%が句切れ不自然を
  出しており、**中程度の相関はあるが「Step1.5が主因」と断定するには弱い**。
- 推奨：**案B相当（品詞・活用形をverse_type別に絞り込む）**を、まず「長句の格助詞
  『に』・接続助詞『て／で／ば』止めを許容する」形で適用するのが最もデータに
  裏付けられた修正。「の」「を」等その他の助詞止めは現状維持を推奨。
- 変更は行っていない（Phase 0のスコープ通り）。

## §1 コード読み取り

### §1-1 `clean_phrase_edges?` 実装全文

`app/services/stepwise_waka_generator.rb:311-324`：

```ruby
# 抽出句の先頭・末尾が語のまとまりとして自然か。
# 先頭が助詞／助動詞／記号（読点など）、末尾が格助詞・接続助詞・係助詞・
# 連体化・並立助詞 で終わる場合は「破れ」とみなす（MeCab標準辞書のfeature列）。
def clean_phrase_edges?(morphemes)
  return false if morphemes.nil? || morphemes.empty?

  head = morphemes.first[:feature].split(",")
  tail = morphemes.last[:feature].split(",")
  return false if %w[助詞 助動詞 記号].include?(head[0])
  return false if tail[0] == "助詞" && %w[格助詞 接続助詞 係助詞 連体化 並立助詞].include?(tail[1])

  true
end
```

**句末（tail）判定**：feature[0]（品詞大分類）が`"助詞"`かつfeature[1]（品詞細分類）が
`[格助詞, 接続助詞, 係助詞, 連体化, 並立助詞]`のいずれかなら「破れ」。

MeCab（IPA辞書）での実際の分類を確認した（`natto`で実測）：

| 語 | 分類（文脈依存） |
|---|---|
| 「て」（動詞連用形の後） | `助詞,接続助詞,*,*,*,*,て,テ,テ` → **棄却対象** |
| 「の」 | `助詞,連体化,*,*,*,*,の,ノ,ノ` → **棄却対象** |
| 「を」 | `助詞,格助詞,一般,*,*,*,を,ヲ,ヲ` → **棄却対象** |
| 「に」 | `助詞,格助詞,一般,*,*,*,に,ニ,ニ` → **棄却対象** |

**「て」は全般が接続助詞として一律棄却されている**（品詞細分類での絞り込みは
無い＝案Bの「特定活用形のみ除外」は現状未実施）。**verse_type（長句/短句）による
区別も一切無い**。

**句頭（head）判定**：feature[0]が`[助詞, 助動詞, 記号]`のいずれかなら「破れ」。
tailと異なり**品詞細分類（feature[1]）による絞り込みは無く、大分類のみ**で
一律棄却している（例えば係助詞・終助詞・並立助詞のいずれであっても頭に来れば
棄却）。

### 呼び出し元

`extract_and_validate`（`:230-271`）内、`:246`で1箇所のみ呼ばれる：

```ruby
broken = seg && !clean_phrase_edges?(seg[:morphemes])
```

`seg`はStep4の`extract_mora_segment`が切り出した候補（chouku=先頭17音、
tanku=残り14音）。**Step1.5の出力そのものには適用されない**
（Step1.5は`total_mora_of`による音数チェックのみ）。**Step3の出力に対してのみ、
Step4抽出時に適用される**。したがってStep1.5が直接「て止め」を生成しても、
それ自体はチェックされず、Step1.5の出力が次にStep3へ渡され、Step3が
書き換えた結果に対して初めてこの判定が働く（間接的な影響のみ）。

もう1箇所、`shift_window_to_kigo`（`:279-310`、其の八十五 案F）内`:302`でも
同一メソッドが窓選択の候補フィルタとして呼ばれているが、判定ロジック自体は同じ。

### §1-2 `build_length_adjust_prompt` の句構造指示の有無

`app/services/stepwise_waka_generator.rb:499-524`（案3で数値注入済みの現行版）を
確認した。**句末の形式（て止め・体言止め等）に関する指示は一切含まれていない**。
プロンプトが言及するのは「情景の焦点」「音数の過不足」のみで、文法的な
句切れ・語尾の形についての誘導は無い。したがってStep1.5がある特定の句末形式を
「意図して」生成しているわけではなく、単に自由な書き換えの結果として偶発的に
生じている（§2-2で定量評価）。

## §3 評価と推奨

### 1. 「て」止めは誤検出か？

**部分的にYesだが、今回のデータでは主要因ではない**。
- 実装は「て」（接続助詞）をverse_type非依存で一律棄却しており、構造的には
  長句の「て」止め（水無瀬三吟で26.0%＝主要な技法）を誤検出しうる欠陥を持つ。
- しかし今回のp3 run100データでは、実際に棄却された「て」止め2件は**両方とも
  短句**であり、水無瀬三吟に短句の「て」止め用例が無いことから、この2件自体は
  **妥当な棄却**だった。長句の「て」止め棄却は0件（発生しなかっただけで、
  発生すれば誤検出になる潜在バグ）。
- したがって「て止めが句切れ不自然急増（27.4%→37.0%）の主因」という当初仮説は
  **量的には成立しない**（該当2件／175件＝1.1%）。

### 2. 他に誤検出が疑われるパターンはあるか？

**長句の格助詞「に」止め（14件、tail破れの11.8%・全体の8.0%）が、実データで
確認できた最有力の誤検出候補**。水無瀬三吟で長句の12.0%が「に」止めという
実測比率と、今回14件という発生規模から見て、無視できない量である。

「の」（連体化、49.6%）・「を」（4.2%）・「ば」（4.2%）は水無瀬三吟に
実質的な用例が無く、現状の棄却が妥当と判断する。

### 3. 修正方針の候補（推奨順）

**推奨：案B（品詞・活用形をverse_typeで絞り込む）を、当初提案よりデータに
即した形で適用する**：

- 「て」（接続助詞）そのものより、**「格助詞『に』」と「接続助詞『て・で・ば』」を
  chouku（長句）に限り許容**する方が、実データの裏付けが強い。
- tanku（短句）については現状の棄却をすべて維持する（水無瀬三吟に短句の
  て・に止め用例が無いため）。
- 「の」（連体化）・「を」は長句・短句を問わず現状維持を推奨（用例なし）。

案A（「て」を一律除外）は今回のデータでは効果が薄い（該当2件のみ、
かつその2件は短句で除外すべきでない）ため単独では非推奨。
案C（Step1.5プロンプトで句末形式を誘導）はStep1.5がそもそも句切れの原因の
主要因ではない（§2-2の相関は中程度に留まる）ため、費用対効果が低いと判断する。
案D（現状維持）は、長句「に」止め14件（全体の8.0%）を見送ることになり、
案B適用時の推定救済数（+14件、句切れ不自然全体の-8.0pt相当）を考えると
やや保守的すぎる。

**実装時の注意**：`clean_phrase_edges?`は`extract_and_validate`から`@verse_type`
インスタンス変数にアクセス可能な文脈で呼ばれている（同一クラス内）ため、
`verse_type`引数を追加する変更は局所的に完結できる見込み（Phase 0につき
実装はしない）。
