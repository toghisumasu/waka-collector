## §1 背景

Step3（モーラ調整・31音への書き換え）の成功率が6.2%（129draft中Step4通過8のみ）と
極めて低いことが判明。原因は以下4つの複合欠陥：

| # | 欠陥 | 影響 |
|---|---|---|
| A | Step4抽出が厳格すぎる（17音累積境界要求、境界不一致で全棄却） | 38draft(29%) |
| B | free_textが既に適正（29-33音）でもStep3が無条件実行して破壊 | 22中20 |
| C | Step1.5[25,50]とStep4[29,33]の閾値不整合（デッドゾーン素通り） | 38draft |
| D | feedbackが操作的でなくdeflock（attempt2以降プロンプトが同一） | 45draft(619呼出の約2割が空転) |

今回は低コスト・低リスクの3案（1・2・5）を同時実装する。案4（知識蓄積型プロンプト）は
効果ポテンシャル最大だが不確実性も最大のため、今回は対象外（温存）。

## §2 実装内容（D-33-1準拠：diff提示→承認→実装）

### 案1：Step4抽出境界の緩和
- 対象：Step4のモーラ境界抽出ロジック（`extract_mora_segment` 相当）
- 変更：17音の累積形態素境界を厳密一致要求から「±1音の近傍境界許容」に緩和
- 意図：境界不一致による全棄却（38draft, 29%）を救済する

### 案2：Step3の前ゲート追加
- 対象：Step3呼び出し直前の分岐
- 変更：`free_text` が既に29〜33音の適正範囲内であれば、Step3を呼ばずそのまま次工程へスキップ
- 意図：既に正しい候補をStep3が無用に壊すケース（22中20）を防ぐ

### 案5：feedback文言の操作化 + deflock時のtemp調整
- 対象：Step3のfeedback生成ロジック
- 変更：
  - feedbackを「現在28音です」のような通知型から、「現在28音、あと+3音必要です（○○を補うなど）」のように
    方向（増/減）と量を明示する操作型に変更
  - 同一出力が2回連続した場合（deflock検知）、次attemptのtemperatureを引き上げる
- 意図：「従いようがない」feedbackを解消し、45draftのうち無駄打ちを減らす

## §3 やってはいけないこと

- `:direct` 戦略のコードパスへの影響（`generation_strategy` 分岐の外側の共通コードを触る場合は特に注意）
- Step1.5・Step4以外の無関係な箇所の変更
- 保護ファイル（`app/data/*.yml`, `dict/user_entries.csv`）の変更
- 案3・案4・案6など、今回スコープ外の改善案の実装
- **diff提示・人間承認を経ずに実装へ進むこと**（D-33-1、今回は明示的に本番構造コードの変更のため必須）

## §4 進め方

1. 案1・2・5それぞれについて、変更予定箇所の現状コードと変更案（diff形式）を先に提示する
2. 人間が承認するまで実装に進まない
3. 承認後、3案をまとめて実装
4. ゲートチェック（`bundle exec ruby script/verify_shikimoku.rb` → 116 pass / 0 fail 維持）
5. 10句規模のsmoke test（`:waka_extraction` 戦略、`script/observe_waka_extraction.rb` 相当）を実行し、
   Step3通過率・二山構造の残り方を確認
6. smoke test結果を人間に報告し、100句本番走行に進むかどうかの判断を仰ぐ（今回の依頼スコープは10句までとする）
