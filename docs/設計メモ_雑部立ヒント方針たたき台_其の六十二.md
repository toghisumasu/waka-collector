# 設計メモ:「雑部立ヒント」方針たたき台(其の六十二)

## 前提

其の六十二で収集した4作品(水無瀬三吟・湯山三吟・遺誡百韻・住吉夢想百韻)の恋・旅・述懐の集計データ(連続句数・間隔・折別分布・折内重複)を元に、season_hintと対になる「雑部立ヒント」の設計案をたたき台としてまとめる。まだ承認前の検討段階であり、実装はしない。

## データが示していること(再掲)

| 観点 | 独吟(遺誡・住吉夢想) | 連衆吟(水無瀬・湯山) |
|:--|:--:|:--:|
| 恋の連続句数(平均) | 約3.5句 | 約2.6句 |
| 恋の間隔(平均/中央値) | 12.9 / 12.0 | 9.5 / 7.0 |
| 述懐の間隔(平均/中央値) | 23.0 / 22.0 | 12.1 / 11.5 |
| 旅の間隔(平均/中央値) | 19.2 / 10.0 | 21.4 / 22.0 |

- 恋は4作品とも初表(1-8句)に一切出現しない
- 旅は初表・初裏から使ってよい(遺誡・住吉夢想で実例あり)
- 三の折後半〜名残にかけて恋・旅・述懐が同一折に重なる箇所が4作品に共通して見られる

## 設計方針(たたき台)

### 1. 序盤の部立制限

現在のnext_constraints(D-44-1で配線済み)は禁忌部立(forbidden_bui)と季節ヒント(season_hint)を返す。これに加えて、句番が初表範囲(1-8句)にある間は「恋」を雑部立ヒントの候補から除外する。旅・述懐は制限しない。

### 2. 直近未使用部立の提案ロジック

以下の閾値を目安として、「そろそろ提案してよい」タイミングを判定する:

| 部立 | 独吟モードの目安間隔 | 連衆吟モードの目安間隔 |
|:--|:--:|:--:|
| 恋 | 12句程度 | 7〜9句程度 |
| 述懐 | 20句程度 | 11〜12句程度 |
| 旅 | 10句程度 | 20句程度 |

閾値を超えたら「候補として提案してよい」フラグを立てる形にし、必須化(must_switchのような強制)はしない。恋・述懐・旅は式目上の句数上限はあるが下限はない(恋の連続下限2句を除く)ため、「出さなければならない」ではなく「出してもよい」という緩やかなヒントにとどめる。

### 3. 独吟/連衆吟モードの切り替え

waka-collectorは現状、単一モデル(qwen3:8b)による生成のため実質的に独吟に近い運用だが、kasen-za等の連衆参加を想定するなら、モード切り替えで上記閾値セットを切り替えられるようにしておく。ただし今回のwaka-collector側の対象は独吟モードの閾値のみで良いと考えられる(連衆吟データは参考値として残すが、実装対象は独吟モードに絞る)。

### 4. 恋・旅/旅・述懐の同時提案は許容、恋・述懐の同時提案は禁止

第52号凡例の排他規則(恋かつ旅、旅かつ述懐は許容/恋かつ述懐は不可)をそのままヒント生成のガード条件として使う。「恋」ヒントを出している句の直後で「述懐」ヒントも同時に出す、ということがないようにする(逆も同様)。

## 推奨度の設計イメージ(2026-07-24追記・検討継続中)

強制(next_constraintsのようなON/OFF)ではなく、「候補として提案してよい」度合いをどう扱うかについて、以下のイメージで検討を続ける:

- **必殺技ゲージのイメージ**:間隔が伸びるにつれて推奨度がなだらかに溜まっていき、ある程度溜まったら「使える」状態になる。ただし溜まった瞬間に強制発動するのではなく、「使える」候補として提示されるだけで、実際に切るかどうか(=その部立で詠むかどうか)はC層の生成判断に委ねる
- **馬柱・将棋の評価関数との類推**:単一の閾値変数ではなく、間隔・直前句の軽重・折内の残り句数など複数の弱いシグナルを合成して推奨度を決める、という多因子の考え方
- **参考文献**:『歌仙 永遠の一瞬』(既存の参考文献リストに記載済み)に、実作者の呼吸・間合いの感覚が言語化されている可能性があり、次回読み直して着想を得る予定

この「ゲージ」の比喩は、実装の閾値設計そのものではなく、強制と提案の境目をどう設計するかという方向性のメモとして残す。次回セッションでは、この比喩を具体的な推奨度の合成式(何を要因とし、どう重み付けるか)に落とし込む作業から始める。

## 未解決・要検討事項

- 上記の間隔閾値は4作品・少数サンプルからの経験値であり、統計的に有意とは言えない(其の四十五〜四十九で確認済みの「サンプルサイズでは自然変動と区別しにくい」問題と同根)。閾値は決め打ちにせず、observe_production_hyakuinでの検証を経て調整する前提とする
- 「候補として提案してよい」というヒントをC層プロンプトにどう文言化するか(next_constraintsのforbidden_bui/season_hintと同じ形式で渡すか、別の新規フィールドにするか)は未検討
- 100inプロジェクトの事後フィードバック機構(却下理由の構造化)との連携要否も、この雑部立ヒント設計が固まってから改めて検討する
