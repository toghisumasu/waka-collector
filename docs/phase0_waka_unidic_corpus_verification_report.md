## T2　比較検証スクリプトの実行（依頼書§3③）

### 重大な発見：`WakaUnidicAnalyzer`現行実装の解析失敗バグ

比較を実行したところ、**`WakaUnidicAnalyzer#analyze`が、テストした14ケース中12ケースで例外を発生させ解析に失敗した**（コーパス6文すべて、および後述の補助検証の複合語候補8語中5語）。エラーは主に`Natto::MeCabError: MECAB_NBEST request type is not set`として表面化した。

原因を追跡したところ、根本原因は`app/services/waka_unidic_analyzer.rb:56`の`node.feature.split(",")`にあることが判明した。UniDicのfeature文字列には、**アクセント型欄など一部の値がカンマを含む引用符付きCSVフィールドとして格納されている**（例：「面影」の該当欄は`"0,2,3"`、「て」の該当欄は`"B1SjS,B1S8SjS"`）。素朴な`.split(",")`はこの引用符を認識せず、フィールド内部のカンマでも分割してしまうため、**列数が本来の29列から30列・31列とトークンごとに不規則にぶれる**。`FEATURE_LAYOUTS`は29列の場合しか定義されていないため、ずれた列数のトークンに遭遇するたびに解析全体が失敗する。

`CSV.parse_line(node.feature)`（Rubyの標準CSVパーサー）で同じfeature文字列を解析すると、全ケースで正しく29列に復元されることを確認した（例：「面影」の該当欄は`"0,2,3"`という1つの値として正しく認識される）。**これは`app/`側の実装バグであり、単純な修正（`split(",")`→`CSV.parse_line`への置換）で解消可能と見込まれるが、依頼書の制約（`app/`配下は差分0行）により本Phaseでは修正しない。**

本バグは、依頼書が検証対象とした「行方型過剰分割」（UniDicが正しく複合語を1トークンに保つかという精度の問題）とは**次元の異なる、より根本的な可用性バグ**である。過剰分割の精度を論じる以前に、現行実装のままでは大半の実文入力でUniDic解析そのものが動作しない。

### 副次的発見：96句でIPA本番相当が実際には検出失敗していた

96句「しぬるくすりはこひにえまほし」で、**IPA本番相当のトークン化は「こひ」を「こ」＋「ひ」に分割しており、トークンレベルの完全一致検索では検出できない。** 其の六十六の報告書は、この句を`text.include?("こひ")`という部分文字列一致でTP（正検出）としてカウントしていたが、実際のMeCabトークン境界では一致しない。**これは其の六十六が既に指摘していた「シミュレーション値と実装値の乖離」（逢ふ・おもひで約15ポイント）が、ひらがな拡張語彙についても同様に生じている可能性を示す新規の発見である。** 遺誡百韻23句全体を通したトークンレベルでの再計測（其の六十六のひらがな拡張版26.1%という数値の再検証）は本Phaseのスコープ外だが、次にこの論点を扱う場合の追加検証候補として記録する。

一方、**この同じ96句で、UniDicは「こひ」を1トークンとして正しく保持し、lemma=恋（正しい語彙素）まで得られている。** IPA側が検出に失敗した実例に対して、UniDic側が救済できる具体例が1件確認できたことになる。

**判定：本Phaseで検証した範囲では「なし」。**

根拠：
1. コーパス6句すべてで、UniDicのsurface一致は6/6件がOK（過剰分割による検出漏れは0件）
2. 補助検証の複合語型恋語彙8語のうち7語でUniDicは単一トークンを維持。唯一過剰分割された「行方」は恋語彙ではなく旅・雑語彙であり、依頼書が懸念した「恋語彙の検出漏れ」には該当しない
