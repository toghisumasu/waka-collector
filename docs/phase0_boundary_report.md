## 0. 結論（要約）

**依頼書の仮説A・Bはどちらも部分的にしか当たっておらず、実態はより具体的な
第三の機序だった**。

区切り不一致54件（p5）の内訳は次の2系統に完全に分解できる：

1. **短句（tanku）の算術的な構造的限界（40/54＝74.1%）**：総モーラ29音の
   短句抽出は、`boundary_index_near`が「17音に最も近い境界」を選ぶ仕様上、
   **物理的に成立しない場合が大半**である（後述、机上で証明可能）。
   仮説Aの「極端値への集中」自体は事実だが、**33音側では起きず29音側でのみ
   起きる非対称な現象**であり、「モデルが極端値に寄る」という説明ではなく
   「29音という値そのものが`extract_mora_segment`の仕組み上ほぼ詰んでいる」
   という実装上の限界だった。
2. **長句（chouku）の複合語またぎ（14/54＝25.9%）**：ただしこれは
   **わずか4句（うち2句はdeflockで同一出力が5回繰り返されただけ）**に起因し、
   「モデルが17+14を意識しない」という仮説Bを支持する事例ではあるものの、
   母数はごく小さい。

too_shortの激減（105→27）との関係は、**個々のflow内での「too_short→区切り
不一致」という直接遷移は0件**だった。集団レベルでは、mora=29への着地数が
28→40（+12）、mora=30-33全体でも27→94（機械集計、後述）という形で増加分が
分散しており、too_shortの大半（105件中の大部分）は素直に29-33音域内の
成功または他カテゴリへ移っているが、**新たに29音へ着地した一部が
上記1.の構造的限界にそのままぶつかっている**。

**推奨**：Phase 1では`boundary_index_near`のskip側（tanku限定）で
「target±toleranceの中で最も近い境界」ではなく「残り音数がtake側の
許容下限を満たす最小の境界」を優先する、という改修が有力候補（実装はしない、
評価のみ）。

## §1 コード読み取り

### §1-1 boundary判定の実装

`app/services/verse_text_analysis.rb:40-76`：

```ruby
def extract_mora_segment(morphemes, skip_mora, take_mora, tolerance: 0)
  start_idx = 0
  if skip_mora > 0
    b = boundary_index_near(morphemes, skip_mora, tolerance)
    return nil if b.nil?
    start_idx = b + 1
  end
  remaining = morphemes[start_idx..]
  return nil if remaining.nil? || remaining.empty?
  e = boundary_index_near(remaining, take_mora, tolerance)
  return nil if e.nil?
  phrase = remaining[0..e]
  { surface: ..., yomi: ..., last_morph: phrase.last, morphemes: phrase }
end

def boundary_index_near(morphemes, target, tolerance)
  acc = 0
  best_idx = nil
  best_diff = nil
  morphemes.each_with_index do |m, i|
    acc += m[:mora]
    diff = (acc - target).abs
    if diff <= tolerance && (best_diff.nil? || diff < best_diff)
      best_idx  = i
      best_diff = diff
    end
    break if acc >= target + tolerance
  end
  best_idx
end
```

1. **境界許容の実装**：`boundary_index_near`は形態素を先頭から累積モーラ加算し、
   `target ± tolerance`の範囲に入った形態素の**中で最も差が小さいもの**を選ぶ
   （同点なら先に見つかった方＝手前を優先）。「17音目±1モーラ」という理解は
   概ね正しいが、**tolerance=1のとき実際に許容されるのは16・17・18音の
   3点のみ**で、これらのうち17に最も近いもの（＝17自体があれば17、無ければ
   16か18のうち近い方）が採用される。
2. **「語境界」の定義**：MeCab形態素の切れ目そのもの。**品詞による絞り込みは
   一切ない**（助詞の直後でも動詞の直後でも同列に候補になる。品詞チェックは
   後段の`clean_phrase_edges?`が別途行う）。
3. **見つからない場合の戻り値**：`boundary_index_near`は`nil`を返し、
   `extract_mora_segment`もそのまま`nil`を返す。`extract_and_validate`側で
   `seg`が`nil`になり、他の失敗理由（前句エコー・音数超過・句切れ不自然）に
   該当しなければ「区切り不一致」となる（`stepwise_waka_generator.rb:265-269`）。

**chouku（skip:0, take:17）とtanku（skip:17, take:14）は共に「17音付近の境界」
判定を共有する**（chokuはそれを終端として、tankuはそれを始端として使う）。
この共有部分が両verse_typeの区切り不一致の起点になる。

### なぜmora=29でtankuが構造的に破綻するか（机上検証）

tankuは`skip=17, take=14`。`boundary_index_near`は**target=17に最も近い
境界**を選ぶ（16・17・18のうち差が最小のもの）。総mora=29の場合、
skip境界がどこに決まるかで残りの取れ高が変わる：

| skip境界の位置 | 残りmora | take目標(14±1=13-15)に収まるか |
|:-:|:-:|:-:|
| 16 | 13 | ○（remaining全体を使えばちょうど13） |
| 17 | 12 | ×（最大12音しか残らず13に届かない） |
| 18 | 11 | ×（最大11音） |

**skip境界が「17に最も近い」という理由で17や18に決まった場合、
残りのモーラが構造的に不足し、take側が必ず失敗する**。実際に確認した
p5の実例（`石の冷たさ胸に伝う空高く風遠くを駆け抜ける`、29音）では、
形態素境界が15→18（「空」→「高く」で一気に3音進む）という配置のため
17ちょうどの境界が存在せず、`boundary_index_near`は最も近い18を選択、
結果として残り11音しか無くtake失敗、という経路を直接確認した
（形態素ダンプは付録参照）。**「17に最も近い境界を選ぶ」という
現行ロジックの選択基準そのものが、mora=29という条件下ではむしろ
不利に働く**（16の境界があればそちらを使うべきだが、17によりや近い
18が優先されてしまう）。

### §2-2 区切り不一致サンプル（p5、実際のログから8件）

#### tanku（mora=29、構造的破綻の典型）

1. 句：「石の冷たさ胸に伝う空高く風遠くを駆け抜ける」（29音）
   16-18音目付近：「空」(acc=15)→「高く」(acc=18、ここが採用される)→「風」(acc=20)
   **17音の境界が存在せず18が採用され、残り11音でtake(13-15)に届かない**

2. 句：「遠き雲の端に灯る色肌に触れる静かな手の重ね」（29音）
   16-18音目付近：「肌」(acc=16)→「に」(acc=17、最近接で採用)→「触れる」(acc=20)
   **境界自体は「に」の直後（17ちょうど）で理想的だが、残り12音でtake(13-15)未達**
   （skip境界が16まで戻らない限りtankuの取り高が原理的に足りない）

3. 句：「静けさに包まれし手のひらに風のそよぎやかに過ぎて行く」（29音）
4. 句：「雪の重みに枝きしむ風の行く末に気配遠く消ゆ」（29音）
   （3・4も1・2と同型の「17近傍で切れても残りが12-13音しかない」構造）

#### chouku（deflockで同一出力が反復、複合語が17音をまたぐ典型）

5. 句：「菊の香り指に沁みて雲の行く末思えば遠き風の音」（31音、verse_no=10、
   **同一出力が5 attempt連続で再生成**＝deflock）
   16-18音目付近：「て」(acc=12)→「雲」(acc=14)→「の」(acc=15)→
   **「行く末」で一気にacc=19まで進み16-18を丸ごと飛び越す**（4音の複合名詞）
6. 句：「烏の羽ひらりと苔に露滴るも柳影遠く消ゆる」（32音、verse_no=58、
   **同一出力が5 attempt連続で再生成**＝deflock）
   16-18音目付近：「露」(acc=15)→**「滴る」で一気にacc=19**（4音の動詞）
7. 句：「光の層に目を奪われて立ちどまりし手のひらの静けさ久しき」（33音、verse_no=74）
   16-18音目付近：「て」(acc=14)→**「立ちどまり」で一気にacc=19**（5音の動詞）
8. 句：「石の上に露ひび裂け遠く澄み渡る空風の音街越えて行く」（33音、verse_no=92）
   16-18音目付近：「遠く」(acc=14)→**「澄み渡る」で一気にacc=19**（5音の動詞）

5〜8はいずれも**4〜5モーラの複合語（名詞・動詞）が16-18音の窓を丸ごと
飛び越える**という同一パターン。これは仮説B（モデルが17+14の内部構造を
意識していない）を支持する典型例だが、**該当はp5全体でわずか4句
（うち2句はdeflockで実質1回の失敗が5回計上されているだけ）**であり、
量的な主因ではない。

### §2-3 too_short激減との連動確認

- too_short（絶対数）：p4=105件 → p5=27件（-78件）
- mora=29への着地件数（`step3`出力全体、失敗も成功も含む）：p4=28件 → p5=40件（+12件）
- **同一flow内で「too_short→区切り不一致」と直接遷移した事例：0件**
  （46で確認、句切れ不自然調査で使った手法と同じロジックで検証。
  つまり「同じ句が一度too_short判定を受けた直後に29音へ着地して
  区切り不一致になる」というミクロな遷移は起きていない）

**結論**：too_shortの減少は主に29-33音域への素直な着地（多くは成功、または
他の失敗理由）として現れており、**「too_shortがそのまま区切り不一致に
形を変えた」という単純な図式ではない**。ただし集団レベルでは、
too_shortが減った分の一部（mora=29への着地+12件）が、§2-1で確認した
構造的破綻（発生率71-83%）にそのまま巻き込まれており、**too_short解消の
「副作用」として区切り不一致が増えた、という間接的な因果は支持される**
（直接ではなく統計的な波及効果）。

## §3 評価

### §3-1 仮説A・Bの支持度

- **仮説A（極端値29・33への集中）**：**部分的に支持、ただし非対称**。
  29音側には実装上の構造的な理由（tanku取り高不足）で強い偏りが実在するが、
  33音側（上限）にはむしろ問題が少ない（発生率10.3%以下）。「モデルが
  両極端に寄る」という対称的な説明ではなく、「29音という値が
  `boundary_index_near`のtie-break規則と噛み合わせが悪い」という
  **実装側の非対称な脆弱性**として理解すべき。
- **仮説B（17+14を意識しない生成）**：**支持されるが少数派（14/54＝25.9%）**。
  chouku側4句（実質2句、残り2句はdeflock複製）で複合語が16-18音の窓を
  飛び越える現象を直接確認できた。ただし母数は小さく、区切り不一致
  増加54件の主因ではない。
- **総合**：主因は**仮説Aに近いが、より具体的には`boundary_index_near`の
  境界選択規則（target最近接優先）がtankuかつmora=29という条件で
  構造的に破綻するという第三の機序**。仮説Bは副次的に実在するが小規模。

### §3-2 「17音先行生成」アーキテクチャの概算コスト評価

依頼書提示のStep A/B/C構成について、現行実装との対比で評価する。

**既存Step0相当の有無**：`:waka_extraction`経路（StepwiseWakaGenerator）には
「前句見立て言語化」に相当する専用ステップは存在しない。最も近いのは
Step1の`gaze_block`（`WakaPersona`のペルソナ・視座指定）だが、これは
「どの距離感・感覚で情景を見るか」の指定であり、「歌全体の構想を言語化する」
Step Aとは目的が異なる。**Step Aは新規実装が必要**（既存資産への吸収は
限定的）。

**Ollama呼出回数の比較（概算）**：

| 方式 | 1verse・1draftあたりの呼出回数（実測ベース） |
|---|---:|
| 現行（Step1→1.5→3×最大5） | 実測平均 約5.4回（p5: step1(2.0)+step1.5(4.4)+step3(5.4)/draft、代表値） |
| 提案（A→B→C、C失敗時はCのみ再生成） | 3回（A,B,C各1回）+ C再生成分（実測要、下記） |

提案方式のコストは**Cの独立成功率**に強く依存する。現行のStep3
（31音一括生成）の成功率は5.5-6.8%（p4・p5実測）と低いが、これは
「五七五七七の全体を一度に31音へ収める」という複合タスクだからで、
**Bが17音単体、Cが14音単体という分離タスクであれば、それぞれの成功率は
現行より高くなる可能性がある**（分割により1回あたりの制約が単純化される
ため。ただし未検証・仮説の域）。仮にB・Cそれぞれの単体成功率が
30-40%程度まで改善すれば、期待呼出回数は
`3 + (1/0.35 - 1) ≒ 4.9回`程度となり、**現行の約5.4回と同等かやや少ない
水準**に収まる可能性がある。ただし：

- B（17音単体）が「五七五」の内部構造（さらに5-7-5に切れる）を持つため、
  Cと同型の境界問題がBの内部でも起こり得る（17音を「5+7+5」に割る境界が
  必要なら、今回発見した「17音境界問題」と同型の問題が5音・12音の境界でも
  再発するリスクがある）。
- 「構想（Step A）を保持したままCのみ再生成」という設計は理にかなっており、
  現行のfree_text固定＋feedback蓄積という設計思想と方向性は一致する
  （Step3が既に「free_text本体は変えずfeedbackだけ変える」設計のため、
  実装の心理的距離は近い）。
- 古歌ヒント（BuiDictionary・gaze_path・水無瀬三吟コーパス）の供給は
  いずれも実装済みの資産の転用で追加コストは小さいが、コーパス参照は
  新規のマッチングロジックが必要。

**総合**：呼出回数の観点では**現行とほぼ同等かやや改善する可能性がある
（不確実性大、要smoke計測）**。設計思想（構想保持・失敗単位のみ再生成）は
筋が良いが、B単体の内部でも境界問題が再発しうる点は事前に想定しておくべき。
実装コストは中〜大（Step Aの新規設計、B/Cのプロンプト設計、古歌ヒントの
配線が必要）であり、**今回発見した「mora=29での`boundary_index_near`
tie-break改善」という遥かに小さい修正で区切り不一致の大部分（74.1%）に
対処できる可能性がある**ことを踏まえると、17音先行生成アーキテクチャは
中長期の候補として温存し、まず小さい修正の効果を見てから判断するのが
妥当と考える。
