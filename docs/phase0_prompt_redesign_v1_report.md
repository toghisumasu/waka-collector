# Phase 0 実験報告：prompt_redesign_v1（付句生成プロンプト再設計）

- 対象スクリプト: `script/experiments/prompt_redesign_v1.rb`
- 実行日: 2026-08-05
- 位置づけ: 其の七十五で着手したPhase 0実験（条件A=旧型プロンプト、条件B=新型プロンプト、各5回）の検証結果まとめ。本番RengaGenerator/StepwiseWakaGeneratorは無変更。

## 1. 前句保持チェック（maeku_preserved）が今回N/Aだった理由と転用方針

当初の実装は「前句の語彙が生成結果にどれだけ含まれるか（部分一致・閾値方式）」を見ており、これは目的の取り違えだった。連歌の付句は前句の語彙を再利用するのではなく、意味的に呼応する別の語で応えるのが正しいあり方であり、A・B双方の出力が前句の語彙をほぼ含んでいなかったのは健全な結果だった。

判定ロジックは「前句という素材そのものが生成過程で改変・重複・欠落していないか」を検証する完全一致方式（空白正規化のみ許容）に変更した（`check_maeku_preservation`）。しかし本実験は付句のみを出力させる構成のため、前句がoutputに登場することはそもそもなく、新ロジックでも9件全件`false`（N/A）となった。これは実装の不備ではなく、このチェックが本実験の設計とは無関係であることを意味する。

**転用方針**: このチェックは、前句をプロンプト経由で出力側に含める設計（StepwiseWakaGeneratorの中間ステップなど）を検証する際に、前句の改変・重複・欠落の検出用として再利用する。実際に2026-08-01の実験#10では、前句「山一色に　暮れ渡るなり」が「くれわたるなり　山一色に　暮れ渡るなり」のように語順入れ替え・重複を起こした事例があり、このロジックはそうした事例の検出を想定している。

## 2. 新しい失敗パターンの発見：音数不一致時に断片のまま出力を終える

`output`フィールドが全件「山の露秋風」等、5〜9文字程度の断片になっており、想定していた完結した句（5音・7音）の体裁になっていなかった。

Ollamaの生レスポンス（`response`フィールド、パース前）と`output`を1件比較した結果、両者は完全一致した。すなわちパース・抽出処理の不備ではなく、**qwen3:8bが最初から短い応答しか返していない**ことを確認した。

さらに同レスポンスの`thinking`フィールド（qwen3のreasoning過程ログ）を確認したところ、モデルは目標音数（5音）を認識しつつ「"山の露に秋風"は6音になってしまう」等、音数の数え直しを延々と繰り返し、結局音数の合わないまま断片的な句を最終出力として確定していた。

つまり今回発見された失敗パターンは、**モデルが正確な音数の句を生成できない場合、完結した句を放棄し、音数不一致の断片のまま出力を終えてしまう**というものである。これは既存の「音数超過」「音数不足」とは別種の失敗であり、「そもそも句の体裁が未完成」という新しいカテゴリとして扱う必要がある。

## 3. 次回プロンプト改訂の方針

現行プロンプトは「正確な音数（5音または7音）で」という数値の下限・目標を提示している。しかしこの数値制約自体が、モデルに「音数を数え直す」という不要な思考ループを誘発し、結果として句が未完成のまま断片で終わる失敗パターンを招いている可能性がある。

次回の改訂方針は以下の通り：

- プロンプト側では**数値の下限・目標音数を提示しない**。代わりに「完結した句として出力せよ」という形式面の拘束のみを課す（例：「一つの完結した句を出力してください。音数の調整は不要です」）。
- 音数が目標と合っているかどうかの判定は、モデルに委ねず**Ruby側の機械的チェック（KuValidator等）に一元化する**。既存のStep1.5音数調整（動的推敲、其の七十五で実装済み）のように、生成後に機械的に音数を検証し、必要なら別ステップで調整する構成を継続する。
- これにより、モデルは「句として意味的に完結しているか」という形式面の判断に専念でき、音数の数値管理はRuby側の決定論的処理が担うという、A層/B層/C層の役割分担（CLAUDE.mdのアーキテクチャ方針）に合致した設計になる。
