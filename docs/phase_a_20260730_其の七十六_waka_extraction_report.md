## 1. 結論（要約）

10句の走行は完走したが、`:waka_extraction`方式は**現状のまま百韻規模へ進める状態にない**。

- **レイテンシは問題ではない。** 1呼び出しの中央値は1.6〜4.3秒で、180秒のタイムアウト設定に対して二桁の余裕がある。
- **問題は呼び出し回数である。** 1句あたり平均96.9回・最大176回のOllama呼び出しが発生し、1句平均307.7秒（最大795.7秒）を要した。`:direct`方式の上限（25回/句）を大きく超える。
- **句の成立率が低い。** 10句中 `create`（正規経路での成立）は5句のみ。残り5句はforced_zatsuレスキュー、うち2句はモーラngのまま確定（`forced_zatsu_mora_ng`）。
- **ng率84.0%**（`:direct` sono71_run1 は39.6%）。ただし後述の通り単純比較には注意が要る。
- **A層（ShikimokuChecker）にほとんど到達していない。** 35回の生成試行のうち30回がA層到達前に失敗しており、式目判定まで届いたのは6回のみ。
- 追加診断により、失敗の主因が**Step1におけるペルソナ`gaze_path`の丸写しと、`WakaPersona.best_match`の自己強化ループ**にあることを特定した（第6章）。

## 4. RC-2：タイムアウト超過の有無

**超過あり。180秒タイムアウトが5回発生した。**

| 句 | 試行 | Step | 経過 |
|---|---|---|---|
| v3 | a1 | Step1.5 音数調整 | 180.00秒 |
| v3 | a2 | Step1 自由詠み | 180.01秒 |
| v3 | a4 | Step1 自由詠み | 180.01秒 |
| v5 | a5 | Step1.5 音数調整 | 180.01秒 |
| v10 | a1 | Step1.5 音数調整 | 180.01秒 |

いずれも `RuntimeError: メンタムさんへの接続がタイムアウトしました（180秒）` として `StepwiseWakaGenerator` を貫通し、観測スクリプトの `rescue RuntimeError, Net::ReadTimeout` で「接続タイムアウト」として再試行された。

**重要：これは「処理が重くて180秒かかった」のではない。** 180秒の8割（144秒）以上を要した成功呼び出しは **0回** であり、所要時間の分布は「5秒以下」と「180秒（タイムアウト）」に完全に二分している。すなわちOllama側の無応答ハングであり、レイテンシの連続的な悪化ではない。過去のrun5で疑われたOllama無応答ハングと同種の現象と見られる。

### 依頼書との前提のずれ（記録）

依頼書は「既存300秒設定」としていたが、`StepwiseWakaGenerator` の3つのOllama呼び出しはいずれも `timeout: 180` 固定である（`stepwise_waka_generator.rb:89, 119, 134`）。300秒は `OllamaClient.generate` のデフォルト値であり、`:waka_extraction`経路では使われない（forced_zatsuレスキューの `OllamaClient.chat` のみ300秒）。本報告では実際の設定値である180秒を障害点として扱い、300秒は句単位の参考線として併記した。

参考：1句あたりの累計所要時間が300秒を超えたのは **6句/10句**（v1 381秒、v3 796秒、v5 461秒、v6 343秒、v7 371秒、v10 387秒）。

### 6-1. ペルソナ`gaze_path`の丸写し

9件中6件が「足元に萌え出づる若草の露」で始まる。これは `WakaPersona::PERSONAS[:youth][:gaze_path][0]` の**一字一句そのまま**である（`waka_persona.rb:20`）。モデルは視座を手がかりに詠むのではなく、指示文を転記している。其の七十四で「gaze_path語彙が出力に直接反映され描写の質感が向上した」と評価された挙動は、実は語彙の反映ではなく**逐語コピー**であった可能性が高い。

### 6-2. `WakaPersona.best_match` の自己強化ループ

10句中6句が `best_match` により youth を選択している。原因は次の循環である。

```
youth が「若草・露・光」を含む句を出力
  → その句が次の verse の前句になる
  → best_match が前句から youth のキーワード（若草・露・光・風）を検出
  → 再び youth を選択
  → 再び「足元に萌え出づる若草の露」
```

9句目が典型例で、前句「**糸**よじる**指先光**の筋走り」は語彙的には明らかに woman ペルソナだが、`woman` のキーワード（格子・袖・閨・針仕事・日々・家・灯・衣・庭）に「糸」も「指先」も含まれず、youth の「光」が1点ヒットして youth が選ばれている。其の七十四で既知課題として記録された `best_match` の表記ゆれ・語彙被覆不足の実害が、実データで確認された。

なお依頼書のDon'tに従い、本セッションでは修正を行っていない。

### 6-3. 3句目のnilはこのループの帰結

前句が「足元の若草に露は光りゆく」の状態で youth が選ばれると、Step1は「足元に萌え出づる若草の露…」を返す。`maeku_echo?` は冒頭部分のレーベンシュタイン距離で判定するため（`verse_text_analysis.rb:106`）これが前句エコーと判定され、詠み直しても同じペルソナ・同じ`gaze_path`なので `MAX_CONTENT_RETRIES` の3回とも同一理由で弾かれ、nilに落ちる。**ペルソナ選択が固定化されている限り、内容判定の再試行は原理的に脱出できない。**

### 6-4. seed語の単独出力

5句目はStep1がseed語「かりにや我を」をそのまま返した。プロンプトが明示的に禁じている「連想語だけを単独で出力してはいけません」（`stepwise_waka_generator.rb:276`）に真っ向から反している。

### 6-5. Step1.5閾値（50音／25音）の妥当性

Step1出力9件の音数分布は **7 / 15 / 17 / 19 / 23 / 27 / 27 / 32 / 67**。

- 25音未満（expand発動）：5件
- 50音超（condense発動）：1件
- 適正範囲（スキップ）：3件
- **Step1.5 発動率：67%**

閾値25/50は依頼書の2例（201音・14音）と既存目標値から採用したものだが、実分布の中心は20〜30音付近にあり、**下限25音が分布の中心付近を切っている**。「両極端を補正する」という設計意図に対し、実際には過半の呼び出しでexpandが発動している。閾値の見直しは依頼書のDon'tにより本セッションでは行わないが、実データが揃ったので別課題として起票が妥当。

## 8. 未検証事項

1. **Step3の失敗理由の内訳が不明。** Step3は653回呼ばれて成功は5回（成功率0.8%）だが、失敗理由（`前句エコー` / `N音（三十一音から2音超逸脱）` / `区切り不一致`）の内訳は `StepwiseWakaGenerator#extract_and_validate` 内部に留まりログに出ない。
2. **`extract_mora_segment` の境界厳密性仮説は未検証。** 短句抽出は「累積モーラ数がちょうど17の位置に形態素境界が存在すること」を要求し（`verse_text_analysis.rb:37` の `acc == skip_mora`）、境界を跨ぐ形態素が1つでもあれば `nil` を返す。31音±2に収まっていても五七五と七七の切れ目が形態素境界と一致しなければ通らないため、これがStep3の低成功率の構造的要因である可能性がある。実在の古典和歌（定義上ちょうど五七五七七）を同ロジックに通せばOllama不要で決定的に検証できるが、本セッションでは未実施。
3. **タイムアウト5回の原因。** Ollama側の無応答ハングと推定されるが、Ollamaのログ・リソース状況は確認していない。

## 9. Phase Bへの判断材料

### 所要時間の見積り

1句平均307.7秒より、100句では **約8.5時間**。ただし本走行では10句中5句がforced_zatsuに落ちており、これが100句規模で継続すれば、得られるのは主にforced_zatsuレスキューの挙動データであって`:waka_extraction`の実力ではない。

### 推奨

**依頼書のPhase Bをこのまま実施することは推奨しない。** 理由は3点。

1. **測定対象が測れない。** A層到達率17%では、Phase B目的③（ShikimokuCheckerとの整合性確認）は100句に増やしても有意なデータにならない。
2. **失敗要因が特定済みで、かつ修正可能に見える。** 第6章の通り、ボトルネックはStep1のペルソナ丸写しと`best_match`の自己強化ループにある。これらは`:waka_extraction`という方式そのものの限界ではなく、其の七十四で導入されたペルソナ機構の実装上の問題である。修正前に8.5時間かけて100句を回しても、修正後に再走行が必要になる。
3. **コストが大きい。** 8.5時間の走行に加え、Ollama無応答ハングが5/969回の頻度で発生しているため、長時間走行では中断リスクも高い（run5の前例あり）。

### 次セッションへの提案（優先順）

1. **未検証事項2の検証**（Ollama不要・数分で完了）— `extract_mora_segment` が実在の古典和歌をどの程度通すかを測り、Step3低成功率の構造的要因を切り分ける。
2. **`WakaPersona.best_match` の自己強化ループ対策** — 直近で使用したペルソナの除外、キーワード辞書の被覆拡充（「糸」「指先」等）、あるいは前句からの推定をやめて明示指定にする等。
3. **`gaze_path` 丸写し対策** — プロンプトで語句そのものを与えるのではなく、視座の「方向」だけを与える等の設計変更。
4. **Step1.5閾値の再設定** — 本報告6-5の実分布データを根拠に下限25音を見直す。
5. 上記を反映した上で、改めて少数句での再計測 → Phase B判断。
