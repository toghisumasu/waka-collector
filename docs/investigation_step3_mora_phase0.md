## 0. 結論（要約）

Step3 の低成功率（step4 通過 8/129 draft ＝ **6.2%**）は、単一原因ではなく **4つの独立した欠陥の合成**：

| # | 欠陥 | 影響（129 draft 中） | 層 |
|---|---|---:|---|
| A | **Step4 抽出が厳格すぎる**。総音数が許容内(29–33)でも、MeCab の形態素境界が「ちょうど17音」に来ないと `区切り不一致` で全棄却 | **38 draft（29%）** — Step3が長さを合わせたのに捨てられている | Step4 |
| B | **Step3 は free_text が既に適正でも無条件に実行され、壊す**。free_mora 29–33 で Step3 入りした22 draft のうち **20 が Step3 で破壊**（圧縮しすぎ or 境界崩し） | 22 draft 中 20 | Step3呼び出し制御 |
| C | **Step1.5 と Step4 の閾値が不整合**。Step1.5 は [25, 50] 外だけ調整、Step4 は [29, 33] を要求。**25–28音（18 draft, 通過0）と 34–49音（20 draft, 通過1）のデッドゾーン**が素通りして Step3 に渡り、ほぼ確実に失敗 | 38 draft | Step1.5 |
| D | **feedback が具体的修正指示になっておらず deflock**。attempt2 以降プロンプトが byte 単位で同一（temp 0.5）→ 出力も byte 単位で同一。45 draft が5回とも同一出力 | 45 draft、約110コール空転 | Step3プロンプト |

「圧縮（助詞を削る）に偏る」のは **文言側とモデル解釈側の両方**だが、
**最大の伸びしろは欠陥A（Step4抽出の緩和）**。これだけで通過率が 6% → 推定 35%+ に跳ねる可能性がある。

## 1. Step3 / Step1.5 現行設計の確認

### 1-1. Step3 プロンプト（`stepwise_waka_generator.rb:341–355`）

```ruby
def build_mora_rewrite_prompt(free_text, feedback)
  feedback_note = feedback ? "※前回の書き換え「#{feedback[:ku]}」は#{feedback[:issue]}でした。#{feedback[:message]}\n" : ""

  <<~PROMPT
    以下の和歌の意味や情景のニュアンスを保ったまま、五・七・五・七・七（合計三十一音）の形に書き換えてください。
    三十一音を超えないこと。短すぎるのも誤りです。区切り記号（／や・など）は使わず、一続きの文として書くこと。
    #{feedback_note}
    【書き換え対象】
    #{free_text}

    【出力形式】
    書き換えた和歌だけを一行で出力してください。見出し・説明・前置き・引用符は不要です。
    書き換え：
  PROMPT
end
```

- 温度：`temperature: 0.5`（`:159`）、`model: "qwen3:14b"`、`timeout: 180`。
- リトライ上限：`MAX_REWRITE_ATTEMPTS = 5`（`:37`）。
- **「三十一音を超えないこと」が先頭かつ命令形で強い**。「短すぎるのも誤りです」は後置・弱い。
  → 圧縮方向へのバイアスが文言構造に埋め込まれている。
- 「一続きの文として書くこと」「区切り記号を使わない」＝ **句切れを表面化させない**指示。
  これは Step4 の「形態素境界がちょうど17音に来ること」という要求と**正面から対立**している（後述）。

### 1-2. feedback 文言（`extract_and_validate`, `stepwise_waka_generator.rb:209–217`）

| 失敗種別 | `issue` | `message`（＝ feedback_note に載る指示） |

**評価：どの message も「何を」「どれだけ」直すべきかを含まない。**

  「28音を31音にしろ」は、モデルにとっては「自分では正しく見える句を、理由の分からないまま書き直せ」に等しい。
- 「区切り不一致」に至っては、MeCab トークン境界という**モデルが知覚できない内部条件**をそのまま人間語に訳さず提示している。

### 1-4. Step4 抽出の厳格性（`verse_text_analysis.rb:35–68`, `extract_mora_segment`）

tanku の場合 `waka_extraction_bounds = [17, 14]`（17音スキップ→14音取得）。
`extract_mora_segment` は：

- **累積モーラが「ちょうど17」になる形態素境界が存在しなければ即 `nil`**（`acc > skip_mora` で return nil）。
- その後、残りから**「ちょうど14」になる境界**がなければ `nil`。

`extract_and_validate`（`:197–218`）の順序上、`区切り不一致` が返るのは
**`over`（総音数が29–33外）が false のときだけ**。
→ **`区切り不一致` の38 draft は全て「総音数は適正なのに切り出せなかった」＝ Step3 は仕事をしている**。

実測（`bundle exec rails runner` で今回ログの step3 出力を再解析）：

| step3 出力 | 総音数 | 境界に17あり | 結果 |
|---|---:|---|---|
| 針の先に光が裂けたように糸が静かに震えている | 29 | ✕ | 区切り不一致 |
| 夕暮れの光が格子を透き通らせ指先に染まり消ゆ | 30 | ✕ | 区切り不一致 |
| ひび割れた指に露の重みたまる 遠き風は市井を越えて行く | **31（ちょうど）** | ✕ | 区切り不一致 |
| 露滴る苔の上に朽木裂け目よりかすかに蝉の声 | 29 | ✕ | 区切り不一致 |
| 草庵の軒端に露の滴る音苔の色夕暮れに染まる | 30 | ○(17) | 区切り不一致（残り13音で14に届かず） |

**「ひび割れた指に露の重みたまる／遠き風は市井を越えて行く」は 31音ちょうどの有効な和歌**だが、
MeCab が「たまる(3)」で累積16、「遠き(3)」で累積19 と刻むため17に境界が無く、機械抽出が nil。
Step3 プロンプトが「一続きの文で」と指示しているため、モデルは句切れを作らず、
結果として MeCab 境界が17に一致する確率が下がっている。

## 2. モーラ超過「二山構造」の代表例と考察

per-draft の最終 attempt の step4 結果（129 draft）：

```
区切り不一致 38 / PASS 8 /
低位側(18–28音) 47  ← うち 24音13, 28音9, 27音9, 26音6, 25音5, 23音4, 20音3, ...
高位側(34–41音) 31  ← うち 35音10, 34音8, 36音5, 38音4, 37音2, 39音1, 41音1
```

### 2-1. 低位側（縮めすぎ、18–28音）— n=47

**傾向：助詞・接続の脱落による「電文化」。意味は概ね保たれるが、和歌としては非文法的に痩せる。**

代表例1（draft 1,2,3・free_mora 29 ＝入力時点で適正）：
```
free : 格子の影が戸を潜むとき 風の音がそっと指に触れる
s3[0]: 格子の影戸潜むとき風の音そっと指触れる          → 25音
s3[3]: 格子影戸潜むとき風音指にそっと触れる            → 24音（さらに悪化）
```
「が」「を」「に」を削除。attempt を重ねるほど助詞が減り、音数が下がっていく（収束の逆）。

代表例2（draft 1,1,4・free_mora 24 → Step1.5 expand → 入力 35音相当）：
```
free : 織り目にそそるかすみの色が遠くへと溶けてゆく
adj  : 織り目にそそるかすみの色が遠くへ溶けてゆく空に風の声がただよふ  （expand）
s3   : 織り目そそるかすみ色遠く溶けて空風の声ただよふ   → 28音（×5回すべて同一）
```
Step1.5 が正しく伸ばした（35音相当）のに、Step3 が「31音を超えるな」を過剰適用して
助詞を全部削り 28音まで圧縮。**Step1.5 の仕事を Step3 が打ち消している。**

**「文字数計算が合っていない」のではなく「助詞を削りすぎて意味構造が壊れかけている」。**
モデルは「短い＝古典的で良い」と誤学習しており、31を下回る方向には躊躇がない。

### 2-2. 高位側（縮め足りず、34–41音）— n=31

**傾向：元の詞書風の長文／Step1.5 expand の過剰付加を、Step3 が削りきれない。**

代表例1（draft 1,2,1・free_mora 59 → Step1.5 condense）：
```
free : 指の隙間から漏れる光の粒が、石に沁み込むように冷たくて、肌に触れるとき、その重みがじわりと伝わる。
adj  : 光の粒が石に沁み込むように冷たく、肌に触れるときその重みがじわりと伝わる。 （condense）
s3[0]: 光の粒が石に沁み込むように冷たく肌に触れるときその重みがじわりと伝わる  → 43音
s3[2]: 光の粒石に沁み込む冷たさ肌に触れるときじわり重み伝わる                → 35音（×3回で停滞）
```
2段階（Step1.5 condense → Step3 ×5）かけても 59→35音。**元が長すぎると1パイプラインでは31に届かない。**

代表例2（draft 1,4,5・free_mora 12 → Step1.5 expand が過剰）：
```
free : 織り機の歯がそっと光る
adj  : 織り機の歯がそっと光る　空は静かに暮れゆき　風に揺れる街の気配 （expand、3クローズ足した）
s3   : 織り機の歯に光が差す　暮れる空は静かに　風に揺れる街の気配     → 34音（×5回同一）
```
Step1.5 expand が「遠景を一句」の指示を**二句ぶん**足してしまい、Step3 が1音だけ削って停滞。

代表例3（draft 1,5,2・free_mora 17 → expand）：
```
free : かさなる葉陰に風のささやきけり
adj  : かさなる葉陰に風のささやきけり　空に浮かぶ雲の行く末を思へば
s3   : かさなる葉陰に風のささやきけり　空に浮かぶ雲の行く末を思えば   → 35音
```
上句(かさなる葉陰に風のささやきけり＝16音)は綺麗なのに、expand の付加句が19音あり合計35。
**Step1.5 の付加量が量的に制御されていない**（「一句加えよ」だけで音数指定なし）。

### 2-3. 二山構造の原因（考察）

1. **Step1 が中央値24音と大幅に undershoot**（66/129 が25音未満）。
2. Step1.5 expand は「遠景を一句」という**質的指示のみ**で、付加量が 5〜20音とばらつく
   → 補正後に低位（まだ不足）か高位（付けすぎ）に散る。
3. Step3 は「31を超えるな」を強く効かせるため、
   - 高位から入ると：削り切れずに 34–37 で停滞（安全側で止まる）。
   - 低位〜適正から入ると：助詞を削って 24–28 に落とす（「短い＝正義」バイアス）。
4. **どちらの山も「31 ちょうど」を目標に据えた操作をしていない**。
   Step3 は「超えない範囲でそれっぽく」しか動いていない。

## 4. 改善案（実装しない・複数提示）

各案は独立に適用可能。効果は「今回ログ 129 draft に当てはめた場合の推定通過増」。

### 案1：Step4 抽出を「近傍境界許容」に緩める 〔最優先候補〕

**内容**：`extract_mora_segment` が「ちょうど17音」の境界を要求する代わりに、
16〜18音（±1）の範囲で最も近い形態素境界を採用する。または、
総音数が29–33なら「17前後で切れる境界のうち上句が5-7-5に最も近いもの」を選ぶ。

- **効果**：`区切り不一致` 38 draft の大半が救済。通過率 6% → **推定 30〜38%**。
  （38件は「総音数は適正・Step3成功済み」なので、抽出さえ通れば式目チェックへ進める）
- **コスト**：小。`verse_text_analysis.rb` の純粋関数1つの変更（±20行程度）。
  ただし A層（ShikimokuChecker）に渡る句の音数が厳密31から外れるケースが増えるため、
  下流の音数バリデーション（KuValidator）との整合確認が要る。
- **リスク**：`:direct` 方式は `extract_mora_segment` を使わないため影響範囲は `:waka_extraction` に限定。
  D-72-4（許容誤差±2）の設計思想とは整合。

### 案2：Step3 実行前ゲート（free_text がもう十分なら Step3 を飛ばす）

**内容**：`generate` で `rewrite_and_extract` を呼ぶ前に、
`extract_and_validate(free_text)` を試し、通れば Step3 を丸ごとスキップして採用。

- **効果**：free_mora 29–33 で入って Step3 に壊された 20 draft のうち、
  元々 clean 境界を持つものを救済。**推定 +5〜10 draft**。副次的に総コール大幅減。
- **コスト**：極小（数行）。ただし案1と組み合わせないと「free_text も 区切り不一致」で結局 Step3 送りになる。
- **併用推奨**：案1 → 案2 の順で効く。

### 案3：Step1.5 の閾値を Step4 合格域に合わせ、付加量を数値指定する

**内容**：

  **推定 +8〜15 draft**（Step3 の初期条件が改善するぶん）。
- **コスト**：小〜中。閾値定数＋プロンプト文言＋ `total_mora_of` の結果を prompt に流す配線（±30行）。

### 案4：Step3 を「句割り宣言 → 本文」の2段プロンプトにする（知識蓄積型）

②それを一続きの和歌にせよ」の2部構成にする（1コール内 CoT でも、2コール分割でも可）。

- **効果**：音数の自己検証で二山の両方が中央（31）へ寄る見込み。

- **コスト**：中〜大。プロンプト全面改稿＋出力パーサ（①を捨てて②だけ取る）。

### 案5：feedback を操作的にし、deflock を破る

**内容**：

### 案6：Step3 プロンプトの圧縮バイアスを是正

**内容**：「三十一音を超えないこと」を「**三十一音ちょうどを目指すこと。30〜32音に収めること**」に変更。

## 2. Step3 構造的欠陥の再発有無（§3-2）

### 2-1. 句頭・句末の文法破れ … ほぼ抑止、ただしガードに穴

最終採用100句のうち **5句が句末に読点・句点を残したまま確定**（v2「…色が、」／
v41「…沁みて、」／v49「…溶ける音。」／v50「…絡みつき、」／v52「…光の襞に、」）。
句頭の助詞始まり・句末の格助詞宙ぶらりんは再現なし（第一弾補修が効いている）。

- 原因：`clean_phrase_edges?` は**句頭のみ「記号」を弾き、句末は「助詞（格助詞ほか）」しか見ていない**。
  末尾の読点・句点（`記号`）が素通りする。
- 対処案（小パッチ、次依頼にまとめる）：`clean_phrase_edges?` の tail 判定に
  `tail[0] == "記号"` を追加。または Step3/Step4 出力の末尾約物を単純除去。
- 影響度：品質上は軽微（5%・読点のみ）だが一巻の見栄えに響くため次弾で潰す。

### 2-2. モーラ超過「二山構造」… 100句規模では**未縮小・高位側が復活**

n=10 smoke（run1/run2）では「高位側ほぼ消滅・低位側のみ残存」と観測したが、**100句では両山とも顕在**：
