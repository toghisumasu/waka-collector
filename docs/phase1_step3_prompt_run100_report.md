## 2. too_long / too_short の詳細

`log/stepwise_steps_20260903.jsonl`の`step4`レコード全件（attempt1含む、
`step3_skipped`を除く）を対象に、`issue`文字列から音数を復元し分類した
（`analyze_deflock_mora.rb`のattempt2以降限定の内訳とは異なり、今回は
全attemptを含めた絶対数で比較する）。

| 分類 | p4（絶対数） | p5（絶対数） | 増減 |
|---|---:|---:|---:|
| too_long | 249 | 258 | +3.6% |
| too_short | 105 | **27** | **-74.3%** |
| 句切れ不自然 | 156 | 167 | +7.1% |
| 区切り不一致 | 26 | **54** | **+107.7%** |
| 合計（total step4、非skip） | 640 | 610 | -4.7% |

too_long＋too_short（音数逸脱の合計）で見ると 354件→285件（**-19.5%**）と
全体としては改善しているが、依頼書が名指しした「too_long」単体は動いておらず、
**当初の仮説（上限方向の定性的指示がオーバーシュートを招いている）は
限定的にしか支持されなかった**。実際に効いたのは下限側の明確化だった。

### 区切り不一致が倍増した点について

`build_mora_rewrite_prompt`の固定部分から「三十一音を超えないこと」という
上限限定の表現を「二十九音以上、三十三音以内」という範囲表現に変えたことで、
モデルが下限方向を強く意識するようになった一方、**下限を満たそうとして
言葉を継ぎ足す際に語の切れ目を無視した継ぎ方をする頻度が増えた**可能性がある
（未検証の仮説）。「区切り記号は使わず、一続きの文として書くこと」という
既存の指示は変更していないため、この副作用は今回の変更の直接の意図ではない。
件数自体は26→54とまだ小さい規模（全610件中8.9%）だが、方向として注視すべき。
